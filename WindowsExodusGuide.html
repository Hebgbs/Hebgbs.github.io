Deep compression

Much like how various bagged items can have their physical space minimised by removing the air from it, files on any media can have their “Space” minimised by altering them so repeated data patterns are put into a separate file, which can instruct a system on how to re-assemble it using this reference which when together with the original content takes less space than the unaltered content alone.

This is the ethos of file compression, and it's something you can enable for your whole system partition if you are so-inclined, by visiting the properties dialogue for a device visible in your system device summary (My Computer / This PC) and enabling compression for it.

Continue using your machine as-normal, and eventually it will no longer be compressing anything. If you encounter any errors, ignore them and continue; leave in the background until finished. This process will take anywhere between hours and days depending on how many files are necessary to compress, but the sooner you start, the quicker it'll get done.

If you do this before much else, you can follow the prior advice and perform other tasks to attain comfort operating in a text-only interface, and manage files on the NTFS partition Windows is running from while space is being reclaimed through compression.

Foundation

Now that you've seen a snapshot of what could be during pre-installation, if you'd like to have it for yourself and make it persist between reboots then it must be committed to your on-board or other external storage.

  • Unlike in Windows, where a separate tool is necessary for an external installation; as-long the bootloader and system root are in the same device, an externally-attached system instance can be used across multiple machines, not-unlike what is shown in the pre-installation media's “Live session.”

To that effect, minimally two locations for system software components need to be defined:

  • Root partition mountpoint (/)
  • Boot method

The latter is more-important than the former, and can be solved in a variety of ways, but traditionally the means of booting to an installed instance is handled by a separate bootloader; due in-part to the legacy of general computing but also for convenience: you can still choose to boot into Windows from an alternative bootloader, if you changed your mind last-minute and decided it necessary for an action. There are two primary ways that booting a system is handled, generally based upon whether a system precedes or follows after Secure Boot:

  • Master Boot Record (mbr / msdos)
  • GUID Partition Table (gpt)

The latter-most one is likely what you may have. If an older machine is to be used, then most-likely it uses MBR, which means the NT bootloader will end up being replaced.

  • Without special software, the MBR cannot be manipulated to host more-than one boot method.
  • The bootloader can persist on a separate media, if it is specfied to exist somewhere else. Regardless the boot method used, this is a valid mode of operation; using a USB-attached media for booting to an on-board system instance, so the original on-board / primary boot method isn't overwritten, and thus may render other instances unbootable by “Conventional” means if no other UEFI boot methods for GPT-compatible baseboards are available, without the use of special software such-as Ventoy to select an existing EFI file.

You can also determine how memory pages are stored in any available media during use, which is similar to virtual RAM in Windows; when the “Memory pressure” (as macOS would call it) gets to be a little too much for RAM, your Linux session can handle this in one of two ways as—

  1. …A separate partition (/swap)
  2. …A page file elsewhere
    • Swap files can exist alongside swap partitions, if performing an operatin which requires more memory paging than your on-board modules and dedicated virtual page space allows.

The latter can get a bit tricky, which is why it would be easier to put the pages in a separate partition; less intermediary maths involved since no additional space would be taken by a file otherwise just sitting there and doing nothing, but if you elect to use a swap file, know it could be called whatever you like, so-long that name is used in your filesystem table (/etc/fstab) to mount as the location pages will go, so the system doesn't lock up completely through relief of this “Memory pressure” .

There is also concern about where your stuff goes. Like evrything else above, the location of /home can be in one of two places:

  1. /
  2. Anywhere else

It doesn't even have to conform with expectant behaviour, either; with a little effort, one may move home into a space conventionally prohibited by system installation utilities for convenience-sake; if you want everybody's $HOME to be in the same partition Windows is stored in, then that is totally possible, and may be desired if you cannot afford a lot of space to the root partition without it being inconvenient long-term — especially, if you do not want to juggle which files go where, and would like everything in a single location so your present system backup workflows which are Windows-dependent can still be used, if you prefer that.

Partitioning

Explained prior, minimally you need a space for root and optionally (though it is heavily implied as just-about necessary) a bootloader. Linux Mint — as its predecessors Ubuntu and Debian does — works best with and prefers use of the fourth extended filesystem, (ext4), and as-necessary based on boot method, use of the 32-bit file allocation table (fat32) format for an extensible firmware interface (EFI) system partition (ESP).

  • If you use a Secure Boot-equipped baseboard, and have Windows installed, you already have this; typically, anywhere Windows is installed, you already have a fat-formatted space, which usually is recognised outside of Windows as the first partition of a storage media.

Unlike in Windows where all media just is and recognised as a “Drive” no matter what; depending on device attachment to the baseboard, there will be several designations based on the technology used to transferdata:

  • hd — IDE { “Hard disk” )
  • sd — SATA / M.2 B-key { “Serial device” )
  • nvme — PCI-attached / M.2 E-key { “Non-Volatile Memory Express” )
  • mmcblk — “Card” based media (eMMC, M.2 A-key, “Multi-media card block” )
    • These designations are not strict; different attachments can change how a device is recognised. You can use dmesg, fdisk or lsblk to easily determine what you attached in text-only interfaces, and you can figure out based on contents shown in graphical applications, too which is what.

The remainder of hard disk and serial device assignments are then determined by letter based-on order of attachment (A-Z29; a maximum well-beyond your possession). After the device letter, each partition is provided a numeric designation (1-256; or, half-that in Windows). For memory / flash-based devices, their designation will be based on host controller and port attachment.

Example — the device one could re-use for their ESP to install GRUB at, provided during installation of Microsoft Windows on a GPT-formatted disk, would typically be assigned as one of two locations:

  • sda1
  • nvme0n0p1
    • Yes, this gets even-more confusing with PCI-attached devices; an NVMe SSD will be rendered with the host controller (zero-indexed), as-well the device designation rendered with a number (zero-indexed) instead of a letter. So, nvme1n0p3 would be NVMe controller #2, first device, third partition.

As-explained earlier, Linux-based systems (and other Unix-alikes) operate on different principles than Windows, and this even applies to how devices are recognised; rather than a device being assigned some arbitrary “Drive letter” from antiquity, everything operates from root (/), and all thereafter are a product associated thereof (i.e. /home).

By-default, if an externally-attached media doesn't have any mountpoint associated with it as-assigned in /etc/fstab, it will mount to a location in /media/$USER. These devices should be available through the file manager, when browsing for available devices in the left-side pane. Since the copy of Linux Mint previously-described uses the Xfce desktop, its file manager should be thunar. While this isn't strictly necessary to understand during installation, such knowledge may prove helpful when using external media along with the live session rendered from the USB-attached device you are using to access it.

  • While not necessary to understand later on, an easier way to understand partition assignments may be available in the live session's provided instance of GNOME Disks. If you encounter difficulty comprehending the contents of /etc/fstab, then use of GNOME Disks post-installation may be of interest, but it may not be available by then. To resolve this lack of availability, it may be installed after the fact:
    sudo apt install gnome-disk-utility

During installation, if manual partitioning { “Something Else” ) had been selected, you will be prompted for partition assignments. To ensure comfortable use of your new Linux Mint instance, consider the following:

  • / — 64 GiB (65536 MiB)
  • /boot/efi — Free; this comes with Windows, and can be re-used.
    • Only for gpt-formatted media. If msdos / mbr, bootloader is placed into the hidden 500 mibibytes of space at the device's beginning sector, which will replace the prior bootloader. The bootloader can be put into another device, if-preferred by changing its location in the bottom of Linux Mint's installer, during partition assignment.
    • This is the partition you will want to back up with Clonezilla if-ever you'd like to restore it for Windows mono-boot, usually /dev/sda1
  • /home — 32 GiB (32768 MiB) + 16 GiB (16384 MiB) per-user
    • If using Steam, then either consider a much larger home partition, or modify device assignment(s) in Steam's storage settings.
    • This mountpoint does not need to exist, strictly-speaking; all graphical installers may offer separate /home as an option, but as mentioned prior, $HOME could be anywhere. But while it could also be manually assigned in /etc/passwd and /etc/default/useradd, not everything respects this — in-fact, not all applications will respect the wishes of /etc/default/useradd, and such assignments were from simpler times before journaling filesystems were prevelent; such may be deemed obsolete in-favour for a directory reference link in present-day.

Lastly, if using an older baseboard which only accepts the legacy MBR format, you will still want to manually partition so you can assign an extended partition format. This extended partition is kind-of like a primative of modern-day logical volumes which bandage together multiple devices, in the sense that it's a space which other partitions can be put into; you will need to do this if you have three partitions, and are in need of more-than four, since this fourth partition effectively enables “Virtual” partitions to exist within that space.

  • …Or, rather than working around the physical limit of four partitions in an MBR table, you can potentially follow the prior advice about moving your /home directory to somewhere in the NTFS partition.

    This presumably means you're also using a hard disk, so if you're certain this is the case, then be sure for the NTFS partition, you add prealloc in your NTFS mount options.

Using NTFS for inter-spacial “Symbolic” link references

Establishment of these links will be explained later on. Microsoft's formerly-indomitible position enabled them to incorporate several features which are specific to their Windows platform; one of which being Fast Boot, otherwise-known as Fast Startup. While firmware on lots of older baseboards allow you to disable this feature and return to legacy system operation characteristics, recent baseboards and their firmware seemingly had removed this feature toggle from their various menus. Because of that I have to address this topic as-if you cannot turn it off.

This “Fast boot” feature does one thing really well, and that is to disturb your experience on platforms outside of Windows, because of how its root NTFS partition is kept in a read-only state; if recycling the contents of your Windows root partition, and you had shut down Windows, then rebooting into Linux Mint, let-alone any other Linux-based desktop will result in unexpected dysfunction since the partition Windows is in cannot be written to, which will make appending content into it impossible.

If you are to follow the later advice provided about how to relocate your /home directory, this introduces new problems; it's one thing to be rendered unable of adding content in any directories from your Windows user profile, it's another to be entirely unable of logging in because of this read-only state caused by Windows' modern boot mechanisms. Since .Xauthority cannot be written, the X window server refuses to comply and kick you back out to the display manager.

Of course, fixing this is simple-enough; just reboot the computer into Windows, then select restart from there; everything for it will be unloaded, and the NTFS partition will return to its normal read / write operation. But now the question remains of how to turn off the machine, which is answered simply; power off at the bootloader rather-than shutting down in Windows. You are then at the mercy of your baseboard firmware; since depending on how it operates the power button, you may have to hold that down for several seconds, or it might turn the machine off straight-away.

RAM-paging

DRAM pricing has been absolutely outrageous ever since 2026Q1 for suspecious and political reasons, so many of us will have to make do with the “RAM” we've got, by enabling use of “Swap” space, and perhaps as-well page compression on more-capable machines to ensure continued operation with more than just a couple of applications.

Not many people are aware of this typically, but Windows also has this feature called “Virtual RAM” which is basically what you think it is; rather than storing things to RAM, a virtual extension of it is made for putting background processes into, when they've lingered in RAM disused for a bit, and it'll usually take a little bit longer to reprise background tasks reading from the much, much slower on-board media.

Open-source systems, especially those using the Linux kernel operate on similar ideas, and the ideal result is that performance with a swap file or partition should be similar to virtual RAM in Windows. What Linux can't do is make a slow media feel quicker; if you are already having trouble in Windows, even with a fresh system instance, then your speed improvements will come from less software bloat, telemetry and overall application size, but you remain limited to the speeds and feeds of your media components.

You can elect to not establish a swap space if you don't need it, but there should be provisions to prevent the system from seizing up because of lacking RAM in all systems, regardless how much RAM you may have to prevent it from grinding at a halt due to insufficient RAM, before processs are killed as a last-ditch effort to retain system stability. if you've made a swap space after-the-fact, then it must be defined in the filesystem table. So as an example, in /etc/fstab:

UUID=1234abcd-5678-efab-90fe-dcba76543210 none swap sw 0 0
Unlike swap files, swap partitions are less-arbitrary. The former can be called anything, and be anywhere; the latter is determined more-or-less by the partition's UUID. The following swapfile examples will use generic names, but the names for such can differ from what is shown.

You can also establish a swap file, instead of a partition. Using some advice elsewhere from the Internet, here's a functional example for ext4 filesystems to initialise 8 GiB for immediate use:

You can call this swap file anything, but vmem is used to distinguish the purpose of this swap file. Examples elsewhere often call for using swap or swapfile; the name matters less than /etc/fstab listing the file, and the system recognising its existence.
sudo fallocate -l 8G /vmem
sudo chmod 600 /vmem
sudo mkswap /vmem
sudo swapon /vmem

Then after all of that, add this to /etc/fstab:

/vmem none swap defaults 0 0

For BTRFS root

If you've elected to make BTRFS the root partition format, then the above steps will fail due to the copy-on-write nature of this partition format, which in other cases may be advantageous with intent as a “Soft” backup via file snapshots, but not for this application. To prevent issues, the above must be modified:

sudo mkdir /swap
sudo chattr +C /swap
sudo fallocate -l 8G /swap/vmem
sudo chmod 600 /swap//vmem
sudo mkswap /swap/vmem
sudo swapon /swap/vmem

Afterward, in /etc/fstab:

/swap/vmem none swap defaults 0 0

Remote access

Before executing on this idea of accessing content inter-spacially through directory link references, the partition has to be accessible. One could do this for both now, and later upon next-reboot with the following example commands:

If the output of lsblk is different than shown, then use what you see. Assuming result has Windows root as /dev/sda3.
sudo mkdir /mnt/WinRoot
lsblk -f⇣
sudo mount /dev/sda3 /mnt/WinRoot
sudo echo "/dev/sda3 /mnt/WinRoot ntfs nosuid,nodev,nofail,prealloc,gid=1000,uid=1000,umask=000 0 0" >> /etc/fstab
The provided additional mount options as-shown:
  • prealloc — Never to be used with solid-state media; enables excess allocation of space for files as they are written to mitigate fragmentation across spinning magnetic media.
  • gid=1000,uid=1000,umask=000 — Primarily where file access by applications demand total control of files; gives user 1000:1000 (typically the first user) non-restricted access of the partition, and sets umask to never disallow any file operations for that space. Services like Valve's Steam benefits greatly with this addition.
While the above example using a device identifier will work in well-over 90% of situations, it is highly advised you use the UUID for whatever your Windows root partition is, as-shown with the following:

  • Steam software

  • “The big five”
    Using some terminal magic, we can make five operations happen in one line — No formal programming needed. You can define a variable specifying a source location, and if you're trying to make variables work into your favour, one might be bothersome: $USER. This is because if you used a proper noun for your name in a local account, the case-insensitive Windows will want to use exactly what you gave it, while the case-sensitive Linux instance forces lower-case names for all directories in /home. Assuming our victim example user is “Alice”, she has to do something about that if her name is the “Same” between accounts otherwise:
    cd /mnt/WinRoot/Users
mv ./Alice ./alice
lns=/mnt/WinRoot/Users/$USER && printf "Documents\nDownloads\nMusic\nPictures\nVideos" | xargs -I {} sh -c "mv $HOME/{}/* $lns/{} && rmdir $HOME/{} && ln -s $lns/{} $HOME"
    Now that last one is a lot. So; $lns is the local-scope variable you define with the location for your Windows user profile. printf is being used to produce a newline-delimited array of words as floating-point values which represent the directory names in both the NTFS mount point and $HOME. Since $HOME effectively resolves to /home/$USER, this is why matching names between Windows and Linux user profile directories wotks. The output of printf is piped to xargs for running a sub-shell which delimits however many commands one wishes to execute. Then within the subshell for each line; move contents from $HOME into the defined Windows user profile directories, remove (delete) emptied directories, and create a reference per-directory to $HOME. Not bad for one command.

    cd $HOME
ln -s /mnt/WinRoot/Users/$USER/AppData/Local/Packages/Mozilla.Firefox_n80bbvh6b1yt2/LocalCache/Roaming/Mozilla/Firefox $HOME/.mozilla

    If you aren't using any OS-specific extensions, then everything should work as-intended upon first-boot. Though.
